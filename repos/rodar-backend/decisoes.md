# rodar-backend: decisões

Decisões que valem só para este repositório. Uma linha por decisão, a mais nova no topo. Decisão que muda o plano (fases, critérios, escopo) vai por `/adr` em [`docs/adr/`](../../docs/adr/), e aqui fica só o link.

| Data | Decisão | Por quê | Fonte |
|---|---|---|---|
| 2026-11-28 | Diagnosticada a causa raiz de "a ligação ao recebedor não funciona" (reportado pelo usuário com print da Task RST-4B21): a ligação dispara de verdade (`tasks.loop_escalonamento` → `ligacoes.ligar`), mas em `RECEBEDOR_MODO=rtc` o link da sala (`pagina_recebedor`) não é enviado a ninguém e o painel (`rodar-web`) não o exibe, então sempre termina `nao_atendida`; além disso, `chamados.monitorar` roda em paralelo pro mesmo evento (`on_chegada`) e nunca escala, só loga desistência. Decisão: não corrigir agora, só registrar o achado pra decisão do time (opções levantadas: expor o link no painel, religar/remover o `ChamadoCCO` duplicado, ou configurar `RECEBEDOR_MODO=sip`) | Investigação pedida explicitamente, sem pedido de correção; a mudança tocaria rodar-backend e rodar-web ao mesmo tempo, melhor decidir com o time antes de tocar os dois | sem commit (sessão de diagnóstico, confirmado ao vivo contra `/cco/estado` do backend local) |
| 2026-11-28 | Antes de descartar o `TypeError` da ferramenta de validação (`GET /ligacoes`) como erro de transporte, conferir nos logs do CloudWatch se a causa foi um `5xx` da própria API, em vez de aceitar a hipótese sem prova | O `score.md` apontou que a causa não tinha sido investigada; as 22 chamadas ao endpoint na janela da sessão devolveram `200`, descartando a API como causa — mas `scripts/validar_fluxos.py` não confere o status antes de iterar a resposta como lista, o que vira esse `TypeError` em qualquer erro de transporte; não endurecido nesta rodada | `evidence/validacao.md`, commit `09e6a6b` |
| 2026-11-28 | Travar a imagem do ECS por `:<sha>` numa revision nova da task definition a cada deploy, em vez de só repintar a tag mutável `:latest` no ECR | `:latest` mutável não garante que o ECS puxe a imagem nova na mesma revision (pode ficar rodando a imagem antiga em cache); uma revision nova com a tag do commit é auditável (dá pra ver exatamente qual sha está em cada serviço) e cada deploy é reproduzível | commits `d8af042`, `8b303db` |
| 2026-11-28 | Aceitar `ecs:RegisterTaskDefinition`/`ecs:DescribeTaskDefinition` com `resource="*"` na política IAM da CI, em vez de restringir por família de task | A AWS não suporta ARN de recurso pra essas duas ações — é `"*"` ou nada; documentado em `infra/envs/dev/ci.tf` pra não parecer descuido numa auditoria | commit `d8af042`, aplicado via `tofu apply` (perfil `cdk-manager-dev`) |
| 2026-11-28 | Quando o novo mecanismo de deploy por `:sha` falhou na 1ª tentativa (`cli-input-json` via `file:///dev/stdin`), testar o comando corrigido contra a AWS de verdade (registrar e desregistrar uma task definition de teste) antes de dar o push da correção, em vez de só confiar na leitura do erro | O serviço tinha ficado seguro na revision anterior (sem queda), mas um 2º erro de sintaxe no mesmo mecanismo custaria outro ciclo de CI; mais rápido confirmar o comando exato na própria AWS primeiro | commit `8b303db` |
| 2026-11-28 | O smoke do deploy (`GET /rotas/{id}/ocoren` no fim do `ci.yml`) não pode ter efeito colateral em produção | Antes, cada deploy incrementava `Empresa.ultima_sequencia_ocoren` de verdade só para confirmar que a rota responde — baixo risco prático (ninguém consome OCOREN ainda), mas é sujeira que um jurado técnico notaria. Resolvido com um parâmetro `dry_run` | commit `d8af042` |
| 2026-11-28 | Manter o fallback determinístico da 5e/5e2 conservador — só agir quando o LLM não chamou **nenhuma** ferramenta no turno — em vez de uma heurística mais agressiva (agir sempre que `detalhar_ocorrencia` não foi chamada, mesmo com outra ferramenta chamada) | Testada a versão agressiva: ela reproduz a mesma contaminação que está tentando corrigir (anexa uma fala de outro assunto, ex. "O lacre é 4471", como se fosse a resposta da ocorrência aberta).
